# Cava 项目笔记

> 写给读这个仓库的人：**Cava 是什么、我们试了什么、量到了什么、以及一个"用 C++ 加速 Minecraft 服务端"的项目为什么会以"收益为零"收尾。**
> 结论一句话：**在这套整合包上，把寻路 / 实体 / 红石搬到 C++ 不会让服务器更快；但这个过程留下了一套真的能抓 bug 的验收方法、一个逐位一致的原生内核、和一份关于"该往哪投钱"的硬数据。**
> 全部证据在 docs/CAVA-gates.md（门禁台账）与各子系统台账里，本文是给人读的版本。

---

## 1. 这个项目想干什么

Minecraft 1.20.4 的 Fabric **服务端** mod。做法：Java 21 预览版 FFM 调 C++ 动态库，把三个子系统的内层循环搬到原生侧：

| 子系统 | 直觉上的收益来源 |
| --- | --- |
| 生物寻路（P1） | A* 展开节点、邻居判定、堆操作 —— 纯计算，看着很适合原生 |
| 实体开销（P2） | 密集场景里实体互查是 O(N²)，看着是热点 |
| 红石（P3） | 方块 tick 是 tick 里的大头 |

**铁律**：与同一套整合包、native 关闭时**逐 tick 一致** —— 语义基准是整合包（Carpet/Lithium/VMP/FerriteCore 都在），不是原版。
数字上只有 + - * / 和 sqrt 允许跨边界，编译参数固定，ABI 冻结并带布局自检（任何一侧漂移就 fail-closed 拒绝加载）。

## 2. 结局与数字

| 子系统 | 结果 | 关键数字 |
| --- | --- | --- |
| P1 寻路 | **正确性达标，性能净亏，不接管** | 真实 AI 负载 **−14.75 / −14.71 µs/tick**（成对实测，两次差 0.2%；7 条腿符号全为负） |
| P2 实体 | **净亏，不接管** | core1 **+1.86 µs/次**、core2 broadphase **+6.8 µs/次**；测试场景里推挤调用数 **0** |
| P3 红石 | **让位，0% 加速** | 接管点是**死代码**（Carpet 把 RedstoneWireBlock.update 的全部 3 个调用点都 @Redirect 走了） |
| P4 加固/平台 | **完成** | 熔断/看门狗/fuzz 60 万例/真崩取证/一键回滚；MSVC + MinGW 跨编译器逐位一致（15456 行零差异） |

**默认配置与不装这个 mod 行为一致**（所有接管开关默认关，一键回滚是一个 JVM 参数）。

## 3. 三次转折（本文最值得读的部分）

### 转折一：合成场景快 2～3 倍，真实负载是亏的

大搜索空间的合成场景里，原生确实快：长路径 **2.53x**、迷宫 **3.04x**（修复后 2.16–2.76x）。
但把同一套方法搬到**真实 AI 负载**（40 僵尸 + 1 村民 × 2400 tick）上，结果是 **−14.7 µs/tick**。

差在哪？**真实负载里根本没有大搜索空间**：

- 怪物每次寻路的目标距离 **p50 = 7 格**、p90 = 10 格
- 返回路径只有 7～8 个节点，而原版节点预算是 **560**
- 寻路总耗时只占 tick 的 **7–9%** —— 也就是说，**即使把寻路整块变成免费，收益上限就这么大**

教训：**性能结论必须按真实负载量。** 合成场景快不代表线上快，它只代表"这种形状的活儿快"。

### 转折二：一堆全绿的测试，什么都没发现

在写性能对比之前，P1 的原生接管是"上线"状态，证据听起来很硬：**live 接管 144158 次、自证 96220 次、mismatch 0**。
为了做 on/off 性能对比，我们第一次做了「**开着跑一遍、关着跑一遍，逐字段对结果**」，一对比就炸了：

1. **怪物穿墙**：镜像是世界方块的副本，而"世界变了"的通知**从来没接上**（契约里写的主钩子 ChunkSection.setBlockState 在 18 个 mixin 里根本不存在）。
   复用判据是"**没有失效事件**"—— 没有失效源时，这句话等于"**永不失效**"。实测 native 路径**笔直穿过 8 格实心石头**。
2. **路径被截断**：窗口 = 起点终点包围盒 + 4。最优路径一绕出这个盒子，native 就看不见那段走廊，返回一条截断路径
   （64 节点 vs 128 节点，停在墙前面）。
3. **一个"从来没被比过"的字段**：Path.reachesTarget 在 Java 侧被填反，而比对脚本把键名写成了 reachesTargetFlag（回执里是 reachedTargetFlag）
   ⇒ 两边都取不到值、静默判定"相等"。**那份"逐字段一致"在这一点上是假的。**

为什么之前全绿？因为那些测试是**自证式**的：它们证明"给它同一份数据，它算得对"，而管不了"这份数据本身是不是对的、够不够"。
**"求解器一致"不等于"端到端一致"** —— 这是整个项目最贵的一课。

修完之后（P1-FIX）：两条腿逐字段一致（12/12）、两条"故意改坏必须变红"的对照都变红、跨 tick 失效在真实 tick 推进下验证通过。

### 转折三：赌"跨 tick 复用"，两重输

假设是：既然每次调用都要重推地形快照（占原生每次耗时的 28–30%），那把快照缓存起来跨 tick 复用，也许就能翻正。
实测两重否定：

1. **前提不成立**：复用要求"**同一个矩形**再被求解一次"。真实负载 **1972 次调用 / 1972 次推送 / 跨 tick 复用命中 1 次 = 0.05%**。
   每只怪、每个目标算出来的矩形都不一样 —— 没有第二个相同矩形。
2. **结构上就翻不正**：把推送成本**整块抹零**（常驻镜像都到不了的不可达上界），四条腿仍全部 ≤ 0
   （−14.63 / −7.02 / −7.09 / −2.51）。因为真正的账是「**回退 = 白付一次原生再跑一次 Java**」，比搬运那笔还大。

教训：**在优化一条路径之前，先量它的"命中率/复用率"这类前提**，比优化本身便宜得多，而且能一击致命。

## 4. 工程教训清单（每条都有真实事故）

1. **"绿"不等于"测过"。** 自证式 parity（两种实现在同一份输入上比对）只能证明"算得对"，不能证明"输入对/够"。
   ⇒ 上线判据必须包含**与不接管那条腿的逐字段比对**。
2. **能红的测试才是测试。** 每条结论都要配一个"故意改坏就变红"的对照：关掉窗口守卫 ⇒ 回到 64 节点；关掉失效钩子 ⇒ 穿墙复现；
   把分流阈值改坏 ⇒ 净收益从 0 掉到 −27.4 µs/tick。没有对照的"通过"是运气。
3. **哨兵式判据在没有失效源时是毒药。** "上次 tick != 哨兵值"表示"没发生过失效事件" —— 如果根本没人发这个事件，它永远成立。
4. **同一个事实定义在两处，就会静默漂移。** 寻路的节点类型位号在头文件和内核里各写了一份，**19 个位号全部错位**
   （Java 填"空气"，内核读成"活板门"），而且运行期完全看不出来。⇒ 跨边界的常量/位布局只允许有一处事实来源，要别名就写别名。
5. **计数类的结论必须连命令行一起记。** 平台套件"31 项还是 32 项"取决于有没有传 --expect-rows；
   我因为没记命令行，把子代理**对的**数字判成了错的，后来自己更正了自己。
6. **共享产物目录会让验证被静默作废。** natives/ 有两个生产者，本项目的验证被另一次构建作废过**两次**。
   ⇒ 构建期打印产物指纹（cava: ARTIFACT … size/sha256），任何依赖产物的结论都要记哈希。
7. **"比对"本身也会漏字段。** 键名一个字母之差，就有一整个字段从来没被比过（见转折二第 3 条）。
   ⇒ 用**机械对拍**（脚本字段表 ↔ 回执键名，多一个少一个都要红）代替人眼。
8. **假失败会长得像真结论。** 构建失败留下旧 exe ⇒ 看起来像"9664/10000 不一致"（实际是旧二进制）；
   配置缓存复用"文件存在性"判断 ⇒ 测试被静默跳过而构建是绿的；别的会话的 gradle daemon ⇒ @TempDir 报权限错。
   ⇒ 看到"大规模不一致"先确认被测二进制是刚构建的、命令是真的跑了。
9. **性能必须按真实负载量，而且要拆开算。** 我们量到"接管成功的调用也比 Java 慢 1.22x"这种反直觉结论 ——
   只有把每笔开销拆开（推送 / 上传 / 求解 / 回退）才看得见钱花在哪。
10. **文档是可以被证据推翻的，连 captain 也一样。** 上面第 5 条就是子代理拿证据顶回来的；第 6 条是我先判错别人。
    这个项目的文档体系（门禁台账 + 各子系统台账 + 跨会话提示词）就是为此存在的。

## 5. C++ 跨界经济学（为什么"搬到 C++"不是万能药）

都是本机实测：

| 事实 | 数字 |
| --- | --- |
| Java 调 C++ 一次 | **14–16 ns** |
| C++ 回调 Java 一次 | **26–29 ns** |
| 一次性跨界拷贝一片地形窗口 | 几微秒到几十微秒 |
| 一次寻路要读的方块次数 | 几千到几万（节点预算 × 邻居） |

结论：

- **不能让 C++ 在需要的时候回调 Java 拿方块** —— 26 ns × 几万次 = 毫秒级，比"整片窗口拷一次"贵两个数量级。
  回调是把最贵的东西塞进最内层循环。
- **不能让 Java 把数组地址直接给 C++（零拷贝）** —— Java 对象会被 GC 搬走；能解决这事的 API（critical 区段）在我们的 JDK 21 预览版里**不存在**。
- 所以数据只有两条路：**每次翻译一份**（贵在翻译），或者**从一开始就住在 C++ 那边、两边读同一份**（贵在维护同步）。

**这解释了隔壁 EntityCollisionOptimizer 为什么能快数倍**：它不是"因为用了 C++"，而是
① 挑中的活儿占 tick 的绝大部分（900 只实体就撑爆预算）；
② 把实体状态（每只几个 double）**常驻 off-heap、两边读同一份**，每次调用零翻译；
③ 边界承载"**一次完整查询/一整轮推挤**"，固定开销被几千次运算摊薄；
④ 用 SoA + AVX2 把包围盒比对做成数据并行。
本项目的三个目标，**四条判据一条都不满足**。

## 6. 如果重来一次

1. **第一天就先量 tick 构成，并且把"如果目标占比 < 5% 就重新评估优先级"这条判据执行到底。**
   P0 阶段其实做了 spark 采样，但寻路/实体两格因为本机采样器限制没采到，这条判据就悬空了 ——
   直到最后用**直接插桩**才量出"寻路占 7–9%"。这一步该早三个月做。
2. **先造"两条腿逐字段比对"的 harness，再写第一行原生代码。** 本项目是反过来做的，
   于是"全绿的测试"和"真实行为"之间隔了三个月才发现有两个会穿墙的缺陷。
3. **选目标用那张四条判据的表筛**（占 tick 多少 / 内层是不是纯计算 / 数据好不好交 / 能不能批量），
   而不是按"哪个子系统听起来更重"排序。
4. **"默认关闭 + 一键回滚"应该从第一天就有** —— 这一条本项目做对了，它让上面所有失败都停留在实验室里。
