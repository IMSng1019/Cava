# 我把 Minecraft 的寻路搬到了 C++，结果它更慢了

> 一个「用原生代码加速服务端」的项目实录：哪些数字骗了我、我怎么发现它、以及三条可以带走的性能判据。
> 全文数字都是本机实测（MC 1.20.4 / Fabric 服务端 / JDK 21 预览版 FFM / 一套 49 个模组的整合包）。

---

## 先说结论

- **合成场景里，C++ 版快 2～3 倍。**
- **真实负载里，它慢 14.7 微秒/tick（净亏）**，七个独立测试轮次符号全为负。
- 我做的三个子系统，最后**一个都没有上线**。
- 但我拿到了一个比速度更值钱的东西：**一套真的能抓出 bug 的验收方法** —— 它抓出了三个"所有测试全绿时也发现不了"的缺陷。

如果你也想过"把某段 Java 逻辑搬到 C++/Rust 提速"，这篇大概能帮你省几个月。

---

## 1. 我想干什么

Minecraft 服务端有一个特点：**主线程串行跑整个世界的 tick**（红石、实体 AI、移动、方块 tick 都在里面）。所以"哪里烫就优化哪里"是很自然的想法。

我列了三个候选：

| 子系统 | 直觉上的收益来源 |
| --- | --- |
| 生物寻路 | A* 展开节点、邻居判定、堆操作 —— 纯计算，看着特别适合原生 |
| 实体开销 | 密集场景下实体互查是 O(N²)，看着是热点 |
| 红石 | 方块 tick 占 tick 的大头（实测 36%） |

做法：Java 21 的 FFM（`java.lang.foreign`）调用一个 C++ 动态库，把内层循环搬过去。
铁律只有一条：**必须和 native 关闭时逐 tick 完全一致** —— 一个方块都不能差，一个 tick 都不能偏。

（这条铁律不是洁癖：Minecraft 的红石机器、刷怪塔、村民交易全部依赖原版实现细节。差一点，玩家的机器就坏。）

---

## 2. 先尝到的甜头

我先在**合成的大搜索空间**里量：128 格长路径、迷宫、绕障碍。结果很好看：

| 场景 | Java 关闭时 | C++ | 倍数 |
| --- | --- | --- | --- |
| 128 格长路径 | 592.6 µs | 266.8 µs | **2.53x** |
| 迷宫（200 节点） | 658.2 µs | 273.5 µs | **2.62x** |
| 迷宫（503 节点） | 1861.5 µs | 636.7 µs | **3.04x** |

到这一步，一切都很美好。于是我把同样的方法搬到**真实负载**上。

---

## 3. 然后现实给了我一巴掌

测试场景：40 只僵尸 + 1 个村民，跑 2400 个 tick。

结果：**−14.75 µs/tick**（净亏）。为了排除噪声，我用了"成对"测法 —— **同一次调用里把 Java 和 C++ 两条路都跑一遍**，两次独立测量差 **0.2%**。跨腿的七条腿符号全为负。

为什么？三个数字说明一切：

**① 真实负载里根本没有"大搜索空间"。**
怪物每次寻路的目标距离：**中位数 7 格**（p90 = 10 格），走出来的路径只有 7～8 个节点。而原版的搜索预算是 **560 个节点** —— 它压根用不满。
我造的那些 128 格、500 节点的场景，**在这套整合包里不会自然发生**。

**② 天花板本身就很低。**
寻路在这套负载里总共只占 **34～45 µs/tick ≈ 一个 tick 的 7～9%**。
也就是说：**哪怕寻路整块变成免费，我也只能省这么多。**

**③ 真正的账不是"搬运"，而是"白跑"。**
C++ 每次调用要先把这片地形翻译成扁平表递过去，这笔"搬运"占原生耗时的 **28～30%**。
但我做了个上界实验：**把这笔钱整块抹掉**（任何缓存方案都到不了的理想状态），四条腿**仍然是负的** —— 因为三分之一的调用会"回退"：C++ 说"我这窗口不够可信"，于是 Java 再算一遍。**一次回退 = 白付一次原生 + 再跑一次 Java。**

---

## 4. 比"没收益"更吓人的事

在写性能对比之前，这个原生寻路是"上线"状态，而且证据看起来很硬：

> 原生接管 **144158 次**、自证 **96220 次**、不一致 **0**。

为了做 on/off 性能对比，我第一次做了「**开着跑一遍、关着跑一遍，逐字段比对结果**」。一对比就炸了：

**缺陷一：怪物会穿墙。**
C++ 那边拿的是世界方块的**副本**，而"世界变了"的通知**从来没接上**（设计文档里写的主钩子，在 18 个 mixin 里根本没实现）。
复用的判断条件是"**没有发生过失效事件**" —— 而根本没人发这个事件，于是这句话等于"**永不失效**"。
实测：C++ 算出的路径**笔直穿过 8 格实心石头**。

**缺陷二：路径被截断。**
搜索窗口 = 起点和终点的包围盒 + 4 格。最优路径一旦绕出这个盒子，C++ 就看不见那段走廊，于是返回一条截断的路径 ——
64 个节点、停在墙前面；而 Java 版是 128 个节点、绕过墙到达终点。

**缺陷三：有一个字段，从来没有被比过。**
`Path.reachesTarget` 在 Java 侧被填反了；而比对脚本里把键名写成了 `reachesTargetFlag`（实际回执里是 `reachedTargetFlag`）——
两边都取不到值，脚本静默判定"相等"。
换句话说：**我那份"逐字段一致"的报告，在这一点上是假的。**

### 为什么之前全绿？

因为那些测试是**自证式**的：它们证明的是"给 C++ 同一份数据，它算得对"。
它们**管不了**"这份数据本身是不是对的、够不够用"。

> **"求解器一致"不等于"端到端一致"。** 这是我这个项目最贵的一课。

---

## 5. 那我是怎么把它抓出来的

三个动作，都很土，但有效：

1. **两条腿逐字段比对**：同一个场景，native 开一遍、关一遍，比节点数、末节点、路径长度、整条节点序列的哈希、穿墙计数……
2. **故意改坏必须变红**：每一条"通过"都要配一个反面对照。比如把窗口守卫关掉 ⇒ 必须回到"64 节点停在墙前"；
   把失效钩子关掉 ⇒ 必须重现穿墙。**做不出反面对照的"通过"，都是运气。**
3. **字段机械对拍**：脚本要比的字段表 ↔ 回执里真实出现的键名，多一个少一个都要红。
   （这条就是被上面那个"一个字母的笔误"逼出来的。）

修完之后：两条腿 12/12 逐字段一致，两条反面对照都变红，跨 tick 的失效在真实 tick 推进下验证通过。

---

## 6. 红石：最反直觉的一次放弃

红石看起来最肥 —— 实测方块 tick 占 tick 的 **36%**。但我最后**一个字都没写**，理由很硬：

**接管点是死代码。** 这套整合包装了 Carpet，`fastRedstoneDust` 一开，原版的红石更新方法 `RedstoneWireBlock.update`
**的三个（也就是全部）调用点都被重定向**到了 Carpet 自己的算法。任何挂在那上面的原生钩子，都是**永久静默失效** ——
不是"慢一点"，是"永远不执行"。服务器一切正常，日志干干净净。

**而且红石的内层结构和寻路是反的。**
寻路的内层是"在一份镜像好的地形上做纯计算"（所以搬得动）；红石的内层是"**边遍历边改世界**"，
还夹着 8 个"任何 mod 都能覆写"的虚调用（读方块、写方块、通知邻居、能不能存活……），并且**故意用随机数决定更新顺序**。
搬进原生只有两条路：把整个世界行为面镜像过去（无界），或者每次操作跨界调一次 Java —— 后者**比它替换掉的那次 Java 调用还贵**。

再加上：现有的差分夹具**区分不出这条 Carpet 规则开还是关**，也就是说"世界哈希一致"这句话**证明不了红石是对的**。

结论：收益已被 Carpet 和 Lithium 拿走，剩下的接管点是空的。**让位。**

---

## 7. C++ 跨界经济学：为什么"搬数据"是致命的

都是实测数字：

| 动作 | 成本 |
| --- | --- |
| Java 调 C++ 一次 | **14～16 ns** |
| C++ 回调 Java 一次 | **26～29 ns** |
| 一次性拷贝一片地形窗口 | 几微秒到几十微秒 |
| 一次寻路要读的方块次数 | 几千到几万（节点预算 × 邻居） |

所以：

- **不能让 C++ 在需要的时候回调 Java 拿方块**：26 ns × 几万次 = **毫秒级**，比"整片窗口拷一次"贵两个数量级。
  回调等于把最贵的东西塞进最内层的循环。
- **不能让 Java 直接把数组地址给 C++（零拷贝）**：Java 的对象会被 GC 搬走；能解决这个问题的 API（critical 区段）
  在我用的 JDK 21 预览版里**根本不存在**。

于是数据只有两条路：

1. **每次翻译一份**（贵在翻译）—— 我走的就是这条；
2. **从一开始就住在 C++ 那边，两边读同一份**（贵在维护同步）。

这也解释了隔壁一个同类项目（EntityCollisionOptimizer）为什么能快好几倍。它赢的不是"C++"，是：

1. 挑中的活儿**占了 tick 的绝大部分**（密集实体场景，900 只实体就撑爆 tick 预算）；
2. 把实体状态（每只就是几个数字）**常驻 off-heap，两边读同一份**，每次调用零翻译；
3. 边界承载的是"**一次完整查询 / 一整轮推挤**"，固定开销被几千次运算摊薄；
4. 用 SoA 布局 + AVX2 把包围盒比对做成数据并行。

**四条里有三条跟语言无关。**

## 8. 所以什么时候才值得把一段逻辑搬到 C++

四条判据，**全部**成立才值得动手：

| 判据 | 说明 |
| --- | --- |
| 1. 那块活儿**占 tick 足够大** | 先量再改。占 5% 的活儿，搬到原生快 3 倍也只省 3%。 |
| 2. 内层是**纯计算** | 不是"边遍历边改世界"、不是"调用一堆可被覆写的虚方法"。 |
| 3. 数据**能便宜地交过去**（最好两边读同一份） | 每只实体几个 double 可以常驻共享；整个世界的方块不行。 |
| 4. 能**一次调用干一整批** | 每只怪调一次 vs 一次吃掉整批查询，固定开销差几千倍。 |

> **C++ 不是加速手段，它是「把大块、规整、可批量、数据便宜的计算搬出 JVM」的手段。**
> 目标选错的时候，语言再快也救不回来。

顺便说一句：这套整合包已经装了 Lithium、ServerCore、Carpet、VMP、FerriteCore —— **好摘的果子早被 Java 侧摘走了**。
这也是"三个子系统全部没收益"的最现实的一条原因。

---

## 9. 这个项目最后留下了什么

速度收益是 0，但产出不是 0：

1. **一套真的能抓 bug 的验收方法**（两条腿逐字段比对 + 故意改坏必须变红 + 字段机械对拍），
   它抓出的三个缺陷，在全绿的单腿测试里永远看不到；
2. **一个被证明逐位一致的原生内核**：14 个结构体的布局自检、任何一侧漂移就拒绝加载；
   MSVC 与 GCC 两个编译器在 15456 行 `+ - * / sqrt` 上**零数值位差异**；
3. **这套整合包真实负载的硬数据**（以前全是"以为"）：寻路距离中位数 7 格、每 tick 0.22 次寻路、
   寻路占 tick 7～9%、区块生成与管理约 60%、自然刷怪 21%；
4. **一张"别往这里投钱"的地图** —— 知道不该做什么，和知道该做什么一样值钱；
5. 以及**默认全部关闭 + 一个 JVM 参数回滚**：所以上面所有失败，都停留在了实验室里。

---

## 写在最后

如果你的目标是"让服务器更快"，我现在的建议顺序是：

**① 配置与模组选择 → ② 单核性能（tick 是单线程的，换颗高主频 CPU 往往比任何代码优化都直接）→
③ Java 侧的算法/分配优化 → ④ 选择性原生加速（过上面那四条判据）→ ⑤ 全量重写（几乎总是最差 ROI）。**

别问"要不要用 C++"，先问：**我想加速的那块活儿，占多少？是什么形状？**
答案出来之后，用不用 C++ 通常就不是一个需要纠结的问题了。
