## `hs_err_truncated_fixture.log` -- what it is and why it is not real

**It is hand-made.** It must never be cited as evidence that a crash happened; it exists only to
prove that the forensics parser *refuses* input it cannot trust.

How it was produced (reproducible):

1. run the P4-C crash probe once, so a real log exists:
   `pwsh -NoProfile -ExecutionPolicy Bypass -File tools/crash-probe.ps1`
   -> `build/p4c-hs-err/hs_err_pid<PID>_probe.log`
2. keep the header block (lines 1..12) and the `Problematic frame:` block,
3. **delete everything from `Dynamic libraries:` onwards** (in that run, line 578),
4. append a deliberately truncated frame line (`# C  [some_module.dll+0x1234` -- no closing bracket),
5. prepend a comment banner saying it is hand-made (so nobody mistakes it for evidence).

Deliberate property: the log still carries a plausible banner, signal, JRE version and problematic
frame -- the *only* thing missing is the module table. That is the interesting failure mode: a
parser that trusts the frame text alone would happily print a verdict for a log that cannot
support one. `tools/hs-err-report.ps1` must exit **2** (`PARSE_FAILED`) on this file.

The other three inputs used by `tools/crash-probe.ps1` are **real** crash logs written by
HotSpot into `build/p4c-hs-err/`; they are not checked in (they contain the machine's
environment block, including user names) and are regenerated by running the script.
